## Architecture Decisions (T-2.1.1, T-2.1.2 & T-2.2.2)

### Fast Path Service Design

**Pattern Matching Strategy:**

- Action patterns: High priority, fire-and-forget evaluation
- Non-action patterns: Lower priority, defaulted to Expert AI
- Ambiguous input: Fail-safe defaults to evaluation_llm
- Performance: Pure regex matching, no LLM inference

**Pattern Categories:**

1. Calendar ops (5 patterns) - Schedule, add, book, create event
2. File ops (5 patterns) - Create, delete, move, copy, rename
3. Task ops (4 patterns) - Create, mark complete, update, assign
4. General action verbs (1 pattern) - send, create, delete, update, etc.
5. Info queries (5 patterns) - What, how, why, tell, explain
6. Analysis (3 patterns) - Analyze, suggest, recommend
7. Status (2 patterns) - Status checks, display requests

**Fail-Safe Guarantee:**

- No exception can crash classification
- All errors default to evaluation_llm routing
- Ambiguous input treated as action (user safety first)

### Input Handler Service Design

**Dual-Mode Input:**

- Text: Direct validation and submission
- Voice: Recording state management + transcription preview
- Both: Routable through FastPathService

**Validation Strategy:**

- Length constraints: 2-10K characters
- Lenient character validation (allow most symbols)
- Whitespace trimming
- Error events emitted for UI feedback

**Recording Lifecycle:**

1. startRecording() → state.is_recording = true
2. updatePartialTranscription() → stream updates for real-time feedback
3. stopRecording() → return TranscriptionPreview
4. confirmTranscription() → submit as FastPathRoutingInput

**Type System Integration:**

- Uses branded ISO8601String for timestamps
- FastPathRoutingInput preparation for classification
- Metadata collection (char_length, word_count, duration, confidence)
- Event emitter for async UI updates

## Key Learnings (Sessions T-2.1.1, T-2.1.2, T-2.2.1 & T-2.2.2)

### L001: Type Brand Integration with Helper Functions

**Discovery:** Initially tried using ISO8601String type directly with new Date().toISOString(), but the branded type requires using the helper function iso8601().

**Pattern:**

```typescript
// ❌ Wrong
timestamp: new Date().toISOString();

// ✅ Right
timestamp: iso8601(new Date().toISOString());
```

**Lesson:** When using branded types, always apply the helper function to the value. The type system prevents raw assignment to enforce runtime safety.

**Confidence:** High (0.95) - Core TypeScript pattern
**Category:** Type System

### L002: EventEmitter Typing in Strict Mode

**Discovery:** Tried to use TypeScript generic EventEmitter<T> for typed events, but strict EventEmitter typing requires using third-party libraries (typed-emitter, eventemitter3) or accepting standard EventEmitter typing.

**Options Evaluated:**

1. Standard EventEmitter - No generic typing, works in strict mode
2. typed-emitter - Additional dependency
3. eventemitter3 - Additional dependency, different API

**Decision:** Used standard EventEmitter with manual type annotations in JSDoc for event handlers. This avoids adding dependencies and keeps the implementation simple.

**Lesson:** Sometimes TypeScript generics add complexity without benefit. Simpler is better when the standard library works.

**Confidence:** High (0.9) - Pragmatic choice
**Category:** Design Pattern

### L003: Transcription Preview Type Duplication

**Discovery:** Created FastPathRoutingInput with `transcript` and `duration_ms` properties, but IPC types already had TranscriptionPreview with `text` and `duration` properties.

**Conflict Resolution:**

- Consolidated to use IPC TranscriptionPreview everywhere
- Updated InputHandler to return IPC TranscriptionPreview
- Removed duplicate definition from input/input.ts

**Lesson:** Check existing type definitions before creating new ones. Duplication creates maintenance burden and type confusion. IPC boundaries should drive the type contract.

**Confidence:** High (0.95) - Important design principle
**Category:** Type System

### L004: Regex Escaping and ESLint Compliance

**Discovery:** Used `\[` in regex pattern, but ESLint rule no-useless-escape flags unnecessary escaping. Square brackets don't need escaping in character classes.

**Before:** `/[^\w\s\-.,!?;:'"()\[\]{}/\\@#$%&*+=~`]/g`**After:**`/[^\w\s\-.,!?;:'"()[\]{}/\\@#$%&\*+=~`]/g`

**Lesson:** Know regex syntax deeply to avoid unnecessary escapes. ESLint helps maintain code quality.

**Confidence:** High (0.95) - Common pattern
**Category:** Code Quality

### L007: Swift-TypeScript IPC via JSON-RPC over stdin/stdout

**Discovery:** Implementing cross-language IPC between Swift and Node.js requires careful protocol design. Using JSON-RPC over stdin/stdout is simple, reliable, and doesn't require native modules or FFI.

**Pattern:**

```swift
// Swift side: Read from stdin, write to stdout
while let line = readLine() {
    handleMessage(line)
}
print(jsonMessage)
fflush(stdout)
```

```typescript
// TypeScript side: spawn child process, pipe stdio
const process = spawn(executablePath, [], {
  stdio: ['pipe', 'pipe', 'pipe'],
});
process.stdout?.on('data', (data) => handleMessage(data));
process.stdin?.write(JSON.stringify(message) + '\n');
```

**Lesson:** stdin/stdout IPC is ideal for Electron-to-native communication because:

- No native module compilation needed
- Cross-platform compatible
- Simple error isolation (stderr for logs)
- Graceful shutdown via signals

**Confidence:** High (0.95) - Well-established pattern
**Category:** Architecture

**Lesson:** AnyCodable pattern enables flexible IPC protocols while maintaining Swift's type safety. Essential for JSON-RPC where params/result types vary by method.

**Confidence:** High (0.9) - Standard Swift pattern
**Category:** Type System

### L009: Signal Handling with DispatchSource

**Discovery:** Swift requires DispatchSource for async signal handling. Using signal() directly doesn't work well with async code. DispatchSource provides clean integration with Swift's async model.

**Pattern:**

```swift
signal(SIGTERM, SIG_IGN)  // Ignore default handler

let source = DispatchSource.makeSignalSource(
    signal: SIGTERM,
    queue: .main
)
source.setEventHandler { [weak self] in
    self?.shutdown()
}
source.resume()
```

**Lesson:** Always use DispatchSource for signals in modern Swift. Provides proper async handling and prevents race conditions.

**Confidence:** High (0.95) - Best practice
**Category:** System Programming

### L012: Swift Actor Isolation and AsyncSequence Access

**Discovery:** FluidAudio's StreamingAsrManager is an actor with actor-isolated `transcriptionUpdates` property. Direct access from Task closures results in: "actor-isolated property 'transcriptionUpdates' cannot be accessed from outside of the actor". The `@preconcurrency` import doesn't resolve this in Swift 5.9.

**Attempted Solutions:**

1. Direct access in Task closure - ❌ Actor isolation error
2. `@preconcurrency import FluidAudio` - ❌ Still blocked
3. Local variable capture - ❌ Same isolation issue
4. `Task.detached` - ❌ No async property access

**Working Workaround:**
Removed real-time streaming updates, only provide final transcription on stop. This avoids actor-isolated AsyncSequence access entirely.

```swift
// Simplified approach without real-time updates
let streamingManager = StreamingAsrManager(config: .streaming)
try await streamingManager.start(source: .microphone)
// ... recording happens ...
let finalText = try await streamingManager.finish()  // Only final result
```

**Lesson:** When libraries expose actor-isolated AsyncSequences without proper access patterns, consider:

- Using completion handlers instead of async streams
- Requesting API improvements from library authors
- Deferring real-time features until actor isolation patterns are resolved
- Document as technical debt with TODO markers

**Confidence:** Medium (0.75) - May have better solutions in Swift 6
**Category:** Concurrency / Workarounds

### L013: Service Integration via Singleton Pattern and Event Forwarding

**Discovery:** When integrating multiple layers (Swift ↔ TypeScript ↔ IPC ↔ UI), using singleton patterns with event emitters provides clean separation of concerns while maintaining stateful connections.

**Pattern:**

```typescript
// Service singletons
const swiftBridge = getSwiftBridge();
const inputHandler = getInputHandler();

// Event forwarding
swiftBridge.on('recording_started', () => {
  inputHandler.handleRecordingStarted();
});

// Lifecycle management
async function initialize() {
  await swiftBridge.start();
  await inputHandler.initialize();
}
```

**Lesson:**

- Singletons ensure single source of truth for stateful services
- Event forwarding decouples layers while maintaining reactivity
- Explicit lifecycle methods (initialize/cleanup) prevent resource leaks
- Each layer listens to its dependency and emits to its dependents
- This creates a unidirectional event flow: Swift → Bridge → Handler → IPC → UI

**Confidence:** High (0.95) - Well-established pattern
**Category:** Architecture / Integration

### L014: Electron App Lifecycle and Cleanup

**Discovery:** Electron apps require careful cleanup on multiple exit paths. The `before-quit` event is essential for async cleanup operations that must complete before the app exits.

**Pattern:**

```typescript
app.on('ready', async () => {
  await initializeServices();
});

app.on('window-all-closed', async () => {
  if (process.platform !== 'darwin') {
    await cleanupServices();
    app.quit();
  }
});

app.on('before-quit', async (event) => {
  event.preventDefault();
  await cleanupServices();
  app.exit(0);
});
```

**Lesson:**

- `ready`: Initialize services (can be async)
- `window-all-closed`: Cleanup on Windows/Linux (non-macOS)
- `before-quit`: Cleanup on macOS (Command+Q, Dock quit)
- Always use `event.preventDefault()` in `before-quit` to ensure async cleanup completes
- Call `app.exit(0)` after cleanup, not `app.quit()` (prevents event loops)

**Confidence:** High (0.95) - Electron best practice
**Category:** Platform / Lifecycle

### L015: TypeScript Unused Variable Detection

**Discovery:** TypeScript's unused variable detection (`ts(6133)`) only flags variables that are written to but never read. A variable used in write operations only (like `currentTranscription = finalText`) will be flagged as unused even if it seems "used" in the code.

**Pattern:**

```typescript
// ❌ Flagged as unused
private currentValue: string = '';
someMethod() {
  this.currentValue = 'new value';  // Written but never read
}

// ✅ Not flagged
private currentValue: string = '';
someMethod() {
  this.currentValue = 'new value';
  return this.currentValue;  // Read somewhere
}
```

**Lesson:**

- If a variable is only written to but never read, it's dead code
- Remove such variables or add read operations if they're needed
- This helps identify unnecessary state tracking
- In our case, removed `currentTranscription` since real-time streaming was deferred

**Confidence:** High (0.95) - Core TypeScript behavior
**Category:** Code Quality / Type System
