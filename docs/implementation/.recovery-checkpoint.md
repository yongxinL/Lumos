## Key Learnings (Sessions T-2.1.1, T-2.1.2, T-2.2.1 & T-2.2.2)

### L001: Type Brand Integration with Helper Functions

**Discovery:** Initially tried using ISO8601String type directly with new Date().toISOString(), but the branded type requires using the helper function iso8601().

**Pattern:**

```typescript
// ❌ Wrong
timestamp: new Date().toISOString();

// ✅ Right
timestamp: iso8601(new Date().toISOString());
```

**Lesson:** When using branded types, always apply the helper function to the value. The type system prevents raw assignment to enforce runtime safety.

**Confidence:** High (0.95) - Core TypeScript pattern
**Category:** Type System

### L002: EventEmitter Typing in Strict Mode

**Discovery:** Tried to use TypeScript generic EventEmitter<T> for typed events, but strict EventEmitter typing requires using third-party libraries (typed-emitter, eventemitter3) or accepting standard EventEmitter typing.

**Options Evaluated:**

1. Standard EventEmitter - No generic typing, works in strict mode
2. typed-emitter - Additional dependency
3. eventemitter3 - Additional dependency, different API

**Decision:** Used standard EventEmitter with manual type annotations in JSDoc for event handlers. This avoids adding dependencies and keeps the implementation simple.

**Lesson:** Sometimes TypeScript generics add complexity without benefit. Simpler is better when the standard library works.

**Confidence:** High (0.9) - Pragmatic choice
**Category:** Design Pattern

### L003: Transcription Preview Type Duplication

**Discovery:** Created FastPathRoutingInput with `transcript` and `duration_ms` properties, but IPC types already had TranscriptionPreview with `text` and `duration` properties.

**Conflict Resolution:**

- Consolidated to use IPC TranscriptionPreview everywhere
- Updated InputHandler to return IPC TranscriptionPreview
- Removed duplicate definition from input/input.ts

**Lesson:** Check existing type definitions before creating new ones. Duplication creates maintenance burden and type confusion. IPC boundaries should drive the type contract.

**Confidence:** High (0.95) - Important design principle
**Category:** Type System

### L004: Regex Escaping and ESLint Compliance

**Discovery:** Used `\[` in regex pattern, but ESLint rule no-useless-escape flags unnecessary escaping. Square brackets don't need escaping in character classes.

**Before:** `/[^\w\s\-.,!?;:'"()\[\]{}/\\@#$%&*+=~`]/g`**After:**`/[^\w\s\-.,!?;:'"()[\]{}/\\@#$%&\*+=~`]/g`

**Lesson:** Know regex syntax deeply to avoid unnecessary escapes. ESLint helps maintain code quality.

**Confidence:** High (0.95) - Common pattern
**Category:** Code Quality

### L005: Pattern Matching Priority Ordering

**Discovery:** When building pattern matching systems, order matters. Higher-priority patterns should be evaluated first to ensure deterministic classification.

**Implementation:**

```typescript
// Sort by priority (descending)
this.actionPatterns = [...ACTION_PATTERNS].sort((a, b) => b.priority - a.priority);
```

**Lesson:** Use explicit priority fields and sort at initialization for maintainability. Makes it clear which patterns take precedence.

**Confidence:** High (0.9) - Design principle
**Category:** Algorithms

### L006: Fail-Safe Defaults in Classification Systems

**Discovery:** When ambiguous classification occurs, choosing the safer default is critical for user experience. In Lumos, ambiguous → action (evaluation_llm) is safer than → non-action (expert_ai) because missed actions are less risky than unexpected action execution.

**Lesson:** Consider safety implications of default classifications. Document fail-safe behavior clearly.

**Confidence:** High (0.95) - Domain specific
**Category:** System Design

### L007: Swift-TypeScript IPC via JSON-RPC over stdin/stdout

**Discovery:** Implementing cross-language IPC between Swift and Node.js requires careful protocol design. Using JSON-RPC over stdin/stdout is simple, reliable, and doesn't require native modules or FFI.

**Pattern:**

```swift
// Swift side: Read from stdin, write to stdout
while let line = readLine() {
    handleMessage(line)
}
print(jsonMessage)
fflush(stdout)
```

```typescript
// TypeScript side: spawn child process, pipe stdio
const process = spawn(executablePath, [], {
  stdio: ['pipe', 'pipe', 'pipe'],
});
process.stdout?.on('data', (data) => handleMessage(data));
process.stdin?.write(JSON.stringify(message) + '\n');
```

**Lesson:** stdin/stdout IPC is ideal for Electron-to-native communication because:

- No native module compilation needed
- Cross-platform compatible
- Simple error isolation (stderr for logs)
- Graceful shutdown via signals

**Confidence:** High (0.95) - Well-established pattern
**Category:** Architecture

### L008: Swift AnyCodable for Dynamic JSON

**Discovery:** Swift's strict type system requires a wrapper type (AnyCodable) to handle dynamic JSON structures in IPC messages. This allows encoding/decoding arbitrary JSON without knowing types ahead of time.

**Implementation:**
